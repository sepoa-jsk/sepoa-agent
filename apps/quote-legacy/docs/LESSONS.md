# 발견 결함 이력 — Java 이식 전 정리

> 작성 2026-08-02 (J0). Node 구현 기간(2026-07-07 ~ 08-02) 중 발견한 결함을
> **성격 중심으로** 정리한다. 재발 방지가 목적이므로 "무엇을 고쳤나" 보다
> **"왜 늦게 발견됐나"** 에 무게를 둔다.
>
> Node 구현은 J2 완료 후 삭제된다. 코드는 사라져도 이 문서는 남는다.

## 1. 마이그레이션 006 백필 — 조건이 '미적용'을 오판해 정상 데이터를 덮어씀

**무엇이 일어났는가**

`006_20260730_phase5c_blocks.sql` 의 백필 5 가 이랬다.

```sql
UPDATE sq_quotes SET onetime_total = supply_amount WHERE onetime_total = 0;
```

`onetime_total = 0` 을 "아직 백필하지 않은 행" 으로 해석했다. 그런데 **특별DC 로 전액
할인된 무상제공 견적은 0 이 정답**이다. 조건이 그 둘을 구분하지 못해, migrate 를 돌릴
때마다 정답 0 이 `supply_amount` 로 되살아났다.

당시 러너는 적용 이력을 남기지 않고 매 실행마다 전 파일을 다시 돌렸다. 그래서
이 UPDATE 는 **migrate 를 돌린 횟수만큼 반복 실행**됐다.

피해 견적 4건:

| 견적 | supply | 할인 | 손상된 onetime | 정답 | 발견 |
|---|---:|---:|---:|---:|---|
| 44 (하겐다즈 기준선) | 2,000,000 | 2,000,000 | 2,000,000 | **0** | 작업 9 |
| 1 | 12,020,000 | 1,000,000 | 12,020,000 | **11,020,000** | 작업 10.5 |
| 4 | 312,200,000 | 12,200,000 | 312,200,000 | **300,000,000** | 작업 10.5 |
| 14 | 294,599,094 | 29,459,909 | 294,599,094 | **265,139,185** | 작업 10.5 |

**왜 늦게 발견됐는가**

세 겹으로 가려져 있었다.

1. **"모든 구문이 멱등이므로 재실행해도 무해하다" 는 전제가 틀렸다.** `IF NOT EXISTS`
   같은 **문법적 멱등**과, 같은 입력에 같은 결과를 내는 **의미적 멱등**은 다르다.
   백필 `UPDATE` 는 문법적으로는 몇 번을 돌려도 되지만 의미적으로는 한 번만 돌아야 했다.
2. **단위 테스트가 DB 상태를 보지 않는다.** `npm test` 70종은 엔진·렌더러·API 를 보지
   견적 테이블의 값을 검사하지 않는다. 손상이 나도 테스트는 계속 통과했다.
3. **증상이 엉뚱한 곳에 나타났다.** 실제로 눈에 띈 것은 기준선 PDF 가 −1,094B 어긋난
   것이었다. 파일 크기 차이를 추적해 들어가서야 DB 값이 바뀐 것을 알았다.

작업 9 는 기준선 견적 44 만 보고 고쳤다. **나머지 3건은 그로부터 하루 뒤,
탐지 쿼리를 전체 테이블에 돌려 보고서야 나왔다.** 하나를 고쳤을 때 같은 조건의
다른 행을 세어 보지 않은 것이 두 번째 실수다.

**Java 에서의 대응**

- **탐지 쿼리를 배포 점검 항목으로 유지한다.** 구버전 006 이 적용된 다른 환경은 여전히
  손상 상태일 수 있다.

  ```sql
  SELECT id FROM sq_quotes WHERE onetime_total = supply_amount AND discount_amount > 0;
  ```

  적중 행이 있으면 손상이다. `025_20260802_fix_006_onetime_damage.sql` 이 복구한다.
  복구 근거는 `total_amount` 다 — 손상된 행은 VAT 포함 총액만 할인 후 금액으로 계산돼
  있고 `onetime_total` 만 할인 전 값이라, `total_amount = ROUND((supply − discount) × 1.1)`
  로 정답을 교차 검증할 수 있다.
- **J4 Flyway 는 한 번 적용한 스크립트를 다시 돌리지 않는다.** 이 결함의 재발 경로가
  구조적으로 막힌다. 다만 **신규 환경에서는 파일이 처음부터 다시 도므로 백필 자체는
  여전히 멱등이어야 한다.**
- 데이터를 고치는 마이그레이션에는 **"고쳐야 할 행" 을 양성 조건으로 쓴다.**
  "아직 안 고친 것 같은 행" 을 음성 조건으로 추정하지 않는다.
- 데이터 보정 후에는 **같은 조건에 걸리는 행 수를 세어 0 인지 확인**한다.

## 2. 009 · 021 DELIMITER — 프로시저 정의가 러너에서 조각나 22문 중 14문 실패

**무엇이 일어났는가**

`009_20260715_master_schema.sql` 은 컬럼 존재 확인을 저장 프로시저로 했다.

```sql
DELIMITER //
CREATE PROCEDURE _add_col(IN tbl VARCHAR(64), ...)
BEGIN
  IF NOT EXISTS (...) THEN
    SET @s = CONCAT('ALTER TABLE ...');
    PREPARE st FROM @s; EXECUTE st; DEALLOCATE PREPARE st;
  END IF;
END //
DELIMITER ;
```

`DELIMITER` 는 **클라이언트 지시어이지 서버 구문이 아니다.** 러너는 파일을 세미콜론으로
쪼개는데, 프로시저 본문 안의 세미콜론까지 잘라 정의가 6조각으로 파열됐다.

결과는 22문 중 **14문 실패**였다.

| 조각 | 오류 |
|---|---|
| `DELIMITER // CREATE PROCEDURE …` | `ER_PARSE_ERROR (1064)` |
| `PREPARE st FROM @s` / `EXECUTE st` / `DEALLOCATE …` / `END IF` / `END //` | 파싱·핸들러 오류 5건 |
| `CALL _add_col(...)` × 8 | `ER_SP_DOES_NOT_EXIST (1305)` |

`021_20260722_labor_role_mapping.sql` 에 **같은 구조가 하나 더 있었다.**

**왜 늦게 발견됐는가**

기록이 증상의 절반만 적고 있었다. 문서에는 "009 에서 멈춰 010 이후가 실행되지 않는다"
고 돼 있었고, 그 자체는 맞았다. 그러나 **009 자신의 컬럼 추가 8건도 전부 실패하고
있었다는 사실은 아무도 적지 않았다.**

무해해 보인 이유는 **운영 DB 에 그 컬럼이 이미 있었기 때문**이다. 과거에 누군가
`DELIMITER` 를 처리할 줄 아는 진짜 mysql 클라이언트로 손수 돌린 것이었다.
**스키마의 현재 상태와 마이그레이션 이력이 어긋나 있었고, 이력이 없으니 그 사실을
확인할 방법도 없었다.** 신규 환경에 설치해 봤다면 즉시 드러났을 것이다.

`021` 을 놓친 이유는 단순하다. **009 를 고칠 때 같은 패턴을 전체 검색하지 않았다.**
`grep -l DELIMITER *.sql` 한 번이면 나왔다.

**Java 에서의 대응**

- **J4 Flyway 로 이관하면 자체 러너가 사라진다.** 세미콜론 분리 로직 자체가 없어진다.
- 현재 스키마를 `V1__baseline.sql` 로 스냅샷하므로 **"수동 적용된 스키마 vs 이력" 의
  불일치가 여기서 정산된다.**
- **결함을 고칠 때는 같은 패턴을 전수 검색한다.** 한 건을 고치면 형제가 있는지 먼저 센다.
- 스키마 변경은 **신규 빈 DB 에 처음부터 적용해 보는 경로**를 반드시 유지한다.
  기존 DB 에서만 검증하면 "이미 있어서 무해한" 결함이 영원히 숨는다.

## 3. `calcBlock` 의 `isLabor` 판정 — 빈 배열에 반응해 전 블록을 인건비로 오인

**무엇이 일어났는가**

블록이 인건비 블록인지 판정하는 조건이 이랬다.

```js
const isLabor = Array.isArray(block.labor) || block.block_code === 'LABOR';
```

`Array.isArray([])` 는 `true` 다. 그래서 **`labor: []` 를 함께 보내기만 해도** 그 블록은
인건비 블록으로 판정됐다. 솔루션 블록이든 셋업 블록이든 상관없었다.

인건비로 판정되면 계산이 `block.items` 가 아니라 `block.labor` 를 소계 대상으로 삼고,
렌더러도 인건비 표로 그린다. 즉 **품목이 있는데 소계가 0 이 되거나, 부록에만 있어야 할
인력 행이 금액표에 올라간다.**

도메인 규칙은 이렇다 — **비-LABOR 블록의 `labor` 는 인력투입계획 부록 전용이다.**
금액에 관여하지 않는다. 이 규칙이 코드 어디에도 적혀 있지 않았다.

**왜 늦게 발견됐는가**

**한 번도 실행되지 않는 경로였다.** 실측 3종에도 기준선 견적에도 "비-LABOR 블록에
`labor` 가 붙은" 데이터가 없었다. 테스트 20종은 실측을 재현하므로 역시 이 경로를
타지 않았다.

즉 **테스트가 통과한 것이 아니라 그 코드에 도달한 적이 없었다.** 커버리지로는
"실행 안 됨" 이지만 테스트 결과로는 그냥 초록이다. 위저드 STEP③ 에서 템플릿 기본값으로
`labor: []` 를 붙여 보내기 시작하면서 비로소 드러났다.

같은 판정이 **서버와 클라이언트 양쪽에** 있었다 (`engine.js` 와 위저드 `recalcBlocks`).
서버만 고쳤다면 화면 미리보기와 PDF 금액이 어긋났을 것이다.

**Java 에서의 대응**

- **J3 에서 판정은 `blockCode == "LABOR"` 하나로 한다.** 컬렉션의 존재·크기를 타입 판정에
  쓰지 않는다.
- **비-LABOR 블록의 인력 행은 부록 전용**이라는 규칙을 엔진과 렌더러 양쪽에 명시한다.
- **프론트엔드는 그대로 이관되므로 `recalcBlocks` 의 판정이 Java 엔진과 일치해야 한다.**
  둘이 갈라지면 미리보기와 PDF 금액이 어긋난다 — J3 의 검증 항목에 넣을 것.
- 실측에 없는 입력 조합은 **테스트가 지켜 주지 않는다.** 도메인 규칙은 테스트가 아니라
  타입·불변식으로 강제하는 쪽이 안전하다.

## 4. `dataUri()` 침묵 실패 — 이미지 빠진 PDF 가 정상으로 보임

**무엇이 일어났는가**

```js
function dataUri(file) {
  try { return 'data:image/png;base64,' + fs.readFileSync(path.join(ASSETS, file)).toString('base64'); }
  catch { return null; }
}
```

파일을 못 읽으면 `null` 을 돌려주고 끝난다. 호출부는 그 `null` 을 그대로 `<img src>` 에
넣는다. **경로가 틀려도 예외가 없고, 로그도 없고, PDF 는 정상적으로 생성된다.**
로고·직인·상하단 밴드만 빠진 채로.

임베드 대상은 4개(`logo` `seal` `band_top` `band_bottom`)다.

**왜 늦게 발견됐는가**

**PDF 가 "만들어졌다" 는 사실이 성공 신호로 쓰이고 있었다.** 파일이 생기고 페이지 수도
맞고 금액도 맞다. 이미지가 있는지는 아무도 세지 않았다.

STEP 1 에서 `lib/` → `src/domain/render/` 로 파일을 옮길 때 `ASSETS` 상대경로가 바뀌었다.
이때 조용히 깨질 수 있었고, 실제로 깨졌다면 **바이트 크기 차이 말고는 단서가 없었을
것이다.** 그래서 그 시점부터 "임베드 개수를 직접 센다" 를 검증 절차에 넣었다.

**Java 에서의 대응**

- **J7 에서 자산 로딩 실패는 예외로 던진다.** 견적서에 직인이 빠지는 것은 무시할 수 있는
  실패가 아니다.
- PDF 검증 항목에 **이미지 XObject 개수**를 유지한다 (기준선 8개).
- 일반화: **파일 읽기·외부 프로세스 호출에서 `catch` 로 기본값을 돌려주지 않는다.**
  기본값이 정당한 경우에만, 그 정당성을 주석으로 남기고 로그를 남긴다.

## 5. 덤퍼 복원기 — 선행 주석까지 걸러 내 INSERT 전량 유실

**무엇이 일어났는가**

이 머신에는 `mysqldump` 가 없어(WSL·Docker 도 없다) `mysql2` 기반 덤프 도구를 직접 만들었다.
덤프 파일은 문장마다 앞에 설명 주석을 붙인다.

```sql
-- 데이터: sq_quotes (11행)
INSERT INTO `sq_quotes` (...) VALUES (...);
-- @@SQ-EOS@@
```

복원기가 문장을 정리할 때 **"주석으로 시작하는 덩어리" 를 통째로 버렸다.** 선행 주석
줄만 벗겨야 하는데 덩어리 전체를 버린 것이다. 결과적으로 **`INSERT` 가 전부 사라졌다.**

복원은 오류 없이 끝난다. 테이블은 전부 생기고 예외도 없다. **행 수만 0 이다.**

같은 도구에 결함이 하나 더 있었다 — 값 안에 센티넬 문자열이 들어 있으면 덤프 전체가
예외로 죽었다(방어 가드가 과했다).

**왜 늦게 발견됐는가**

**발견됐다. 늦지 않았다.** 이 두 건은 스크래치패드 스크립트를 `tools/ops/` 로 승격하면서
붙인 **라운드트립 테스트 10종이 잡았다.**

기록하는 이유는 그 반대 경우가 아찔하기 때문이다. 테스트 없이 2~4차 백업을 돌렸다면
**조용히 빈 복원본을 얻었을 것이고, 그것을 백업이라고 믿었을 것이다.** 4차 백업은
구 작업 20 의 `DROP` 직전 지점이었다.

그래서 검증 도구는 파일을 훑거나 `INSERT` 개수를 세는 것으로 만족하지 않고,
**임시 스키마에 실제로 복원해 원본과 행수·체크섬을 대조하고 스키마를 지운다**
(`tools/ops/dbverify.js`).

**Java 에서의 대응**

- **백업·복원 도구에는 반드시 라운드트립 테스트를 붙인다.** "복원되지 않는 백업은
  백업이 아니다." 검증은 실제 복원까지 가야 한다.
- **배치 SQL 처리에서 "몇 건을 처리했는가" 를 반환하고 확인한다.** 0 건 처리는
  성공이 아니라 신호다.
- 파서·필터를 쓸 때는 **버리는 쪽이 아니라 남기는 쪽을 명시적으로 정의**한다.

## 공통 패턴

**다섯 건 전부 실패가 조용한 유형이었다.**

006 백필은 예외 없이 값을 덮었고, `DELIMITER` 는 다음 파일로 넘어가지 못했을 뿐 이미
있는 컬럼 덕에 무해해 보였고, `isLabor` 는 도달하지 않는 경로라 초록이었고,
`dataUri` 는 `null` 을 돌려주고 PDF 를 완성했고, 복원기는 오류 없이 빈 테이블을 만들었다.
**어느 것도 스택 트레이스를 남기지 않았고, 어느 것도 테스트를 빨갛게 만들지 않았다.**

증상은 전부 **한 단계 떨어진 곳**에 나타났다 — PDF 바이트 크기, 페이지 수, 소계 금액,
행 수. 원인에서 먼 지표를 보고 거슬러 올라가야 했고, 그래서 늦었다.

**Java 이식에서는 예외를 삼키지 말고 표면화할 것.** 특히 세 곳이다.

| 영역 | 하지 말 것 | 할 것 |
|---|---|---|
| **파일 읽기** | `catch { return null; }` 로 기본값 반환 | 예외를 던지거나, 최소한 로그 + 실패 카운트 |
| **외부 프로세스** (헤드리스 Chrome) | 종료 코드·stderr 무시 | 비정상 종료를 예외로. stderr 를 로그에 |
| **배치 SQL** | 영향 행 수를 버림 | 처리 건수를 반환하고 기대치와 대조 |

`catch` 로 기본값을 돌려줘야 한다면 **그 정당성을 주석으로 남기고 로그를 남긴다.**
조용한 기본값은 결함을 정상으로 위장한다.

## 부록 — J7 이관 사항: 리눅스 한글 폰트

구 작업 10.6(리눅스 배포 준비)에서 정리한 내용이다. **작업 10.6 자체는 취소되나
이 항목은 J7 에 그대로 필요하다.**

리눅스 서버에서 헤드리스 Chrome 으로 PDF 를 생성할 때 **`Noto Sans CJK KR` 이 설치돼
있지 않으면 문서 전체가 두부(□)로 렌더된다.**

현재 PDF 폰트 스택은 Pretendard 기준이며, 개발 머신(Windows)에는 시스템 폰트가 있어
드러나지 않는다. **리눅스에서만 나타나는 결함**이다.

**금액·페이지 수 검증으로는 잡히지 않는다.** 글자가 두부로 바뀌어도 레이아웃은 그대로라
페이지 수가 같고, 금액은 DB 에서 읽으므로 대조도 통과한다. 파일 크기조차 크게 다르지
않다. **위 다섯 건과 정확히 같은 "조용한 실패" 유형이다.**

J7 대응:

- 배포 이미지·서버에 `fonts-noto-cjk` 설치를 **전제 조건으로 문서화**한다.
- Thymeleaf 템플릿의 `font-family` 에 `Noto Sans CJK KR` 을 폴백으로 넣는다.
- **PDF 검증에 "한글 표시 육안 확인" 을 필수 항목으로 둔다.** 자동 검증으로 대체할 수 없다.
- `ChromeRunner` 는 플랫폼별 실행 경로 후보를 두되 `CHROME_PATH` 를 우선하고,
  리눅스에서는 `--no-sandbox` 토글이 필요할 수 있다.
